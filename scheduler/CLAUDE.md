# 공통 실행 규칙

이 폴더의 작업 파일(`01-*.md` ~ `04-*.md`)을 실행해 보고서를 만들 때 모든 작업에 적용하는 규칙이다.
작업 파일의 지시와 충돌하면 작업 파일을 따른다. 작업 파일을 편집할 때는 이 규칙을 적용하지 않는다.

## 기본

- 시간대: Asia/Seoul(KST, UTC+09:00). 보고서의 날짜와 시각은 모두 KST로 적고, 해외 사건은 필요하면 현지 시각을 함께 적는다.
- 작업 파일의 일정과 Cron 표현식도 KST 기준이다.
- 보고 언어: 한국어
- "직전 24시간"은 실행 시각부터 거슬러 올라간 24시간(KST)을 뜻한다.
- 보고서 첫 줄은 각 작업이 지정한 제목 형식을 따르고, 둘째 줄에 `기준 시각: YYYY-MM-DD HH:mm KST`를 적는다.

## 정확성

- 모든 정보는 실행 시점의 최신 공개 자료를 웹에서 찾아 검증한다.
- 공식 발표, 릴리스 노트, 정부·기업의 1차 자료를 우선한다. 2차 보도로만 확인되는 내용은 "미확인 보도"로 따로 표시한다.
- 확인되지 않은 수치, 날짜, 버전, 사건, 식별번호(CVE 등)를 만들어내지 않는다. 확인할 수 없는 값은 "확인 불가"로 적는다.
- 정보 발표일과 실제 사건 발생일을 구분한다.
- 최신 자료가 없으면 과거 자료를 신규 정보처럼 재사용하지 않는다.
- 모든 항목에 출처 링크와 실제 발표 날짜를 적는다. 링크는 직접 확인한 원문 URL만 쓰고, 검색 결과 페이지나 추정한 URL은 쓰지 않는다.

## 보고 형식

- 결론과 즉시 필요한 조치를 맨 위에 먼저 적는다.
- 작업에 적힌 항목 수(예: 5~8건)는 목표치다. 해당 소식이 적으면 억지로 채우지 않고 있는 만큼만 적는다.
- 이전 보고에서 다룬 사건은 새로운 변화가 있을 때만 다시 다룬다. 이전 보고는 아래 '결과 저장'의 보고서 폴더에서 확인한다.

## 글쓰기

읽는 사람은 출근 전에 휴대폰으로 훑어보는 개발자다. 자연스러운 한국어로, 짧고 읽기 쉽게 쓴다.

- **어미는 "~습니다"로 통일한다.** 본문 문장은 "~습니다/~합니다"로 끝낸다. "~다"체를 섞지 않는다. 표 칸, 짧은 목록 항목, `headline`은 명사형으로 끝내도 된다.
- **번역투를 쓰지 않는다.** 영어 원문을 옮길 때 문장 구조를 따라가지 말고 한국어로 다시 쓴다.

  | 피할 표현 | 이렇게 |
  |---|---|
  | 조용히 바뀐다·실패한다 (silently) | 오류 없이 바뀝니다, 알림 없이 실패합니다 |
  | ~하는 것이 중요하다·필요하다 | ~해야 합니다, 또는 결론을 바로 씁니다 |
  | 이는 ~을 의미한다 | 그래서 ~합니다 |
  | ~에 대해, ~를 통해, ~에 의해 | 조사를 줄이고 동사로 씁니다 |
  | 해당 ~ | 이, 그, 또는 구체적인 이름 |
  | ~할 수 있다 (확인된 사실에) | 확인된 것은 단정하고, 불확실한 것은 근거와 함께 씁니다 |
  | 호환성을 깨는 변경 (breaking change) 같은 영어 섞어 쓰기 | 우리말로 쓰고, 처음 한 번만 괄호에 원어 |

- **문단은 짧게 쓴다.** 한 문단은 2~3문장, 한 가지 이야기만 담는다. 문단 사이에는 빈 줄을 둔다.
- **굵은 라벨을 줄줄이 늘어놓지 않는다.** 모든 줄을 `**라벨**: 긴 문장`으로 시작하면 읽기 어렵다. 항목마다 무엇이 일어났고 무엇을 해야 하는지 한두 문장으로 먼저 쓰고, 버전·날짜·식별번호처럼 나란히 비교할 값만 표나 짧은 목록으로 정리한다.
- **인용 블록(`>`)은 강조에만 쓴다.** 항목에서 독자가 꼭 가져가야 할 한두 문장(실무에 주는 영향, 해야 할 일)을 항목당 한 번만 인용으로 쓴다. 라벨을 붙이지 않고, 출처·긴 설명·표는 인용에 넣지 않는다.
- **목록은 2단계까지만 쓴다.**
- **이름은 원문 그대로 쓴다.** 제품·API·명령·패키지 이름은 바꾸지 않고, 명령과 코드는 `코드` 표기로 쓴다.

항목 하나는 이런 모양이다.

```markdown
### Claude Code 2.1.316 — Opus 4.8 fast mode 종료 예고

11월 30일부터 Opus 4.8 fast mode 요청은 오류를 반환합니다. 대체 모드는 Opus 5.5 fast mode입니다.

> CI나 스크립트에서 이 모드를 고정해 쓰고 있다면 11월 30일 전에 `settings.json`과 워크플로의 모델 지정을 바꿔야 합니다.

- 발표: 2026-10-31 · [릴리스 노트](https://github.com/anthropics/claude-code/releases)
```

## 작업 유형

각 작업 파일 상단의 `유형`을 따른다.

- **보고서형**: 새 소식이 없어도 보고서를 반드시 저장한다. 실행 기록만 남기고 본문을 생략하지 않으며, 새 소식이 없으면 그 사실을 밝힌 짧은 보고서를 저장한다.
- **조건부 알림형**: 조건이 성립하지 않으면 보고서 파일을 만들지 않고 커밋도 하지 않는다.

## 결과 저장

보고서는 저장소에 Markdown 파일로 저장하고 커밋한다.

1. **이전 보고 확인**: 작성하기 전에 `reports/<작업 ID>/` 아래 보고서(`YYYY/MM/DD.md`, 경로순으로 정렬하면 날짜순이다. 예: `ls reports/<작업 ID>/*/*/*.md | sort`) 중 **실행일보다 앞선 날짜**의 가장 최근 2개를 읽고 이미 다룬 사건을 파악한다. 실행일과 같은 날짜 파일(같은 날 다시 실행한 경우)은 이전 보고로 보지 않는다. 해당 파일이 없으면 첫 실행으로 보고 건너뛴다.
2. **저장 경로**: `reports/<작업 ID>/YYYY/MM/DD.md` (실행일의 KST 날짜. 예: `reports/ai-dev-briefing/2026/11/03.md`). 폴더가 없으면 만든다. `작업 ID`는 각 작업 파일 상단에 있다. 같은 날짜 파일이 이미 있으면 내용을 참고하지 않고 새로 써서 덮어쓴다.
3. **파일 형식**: 맨 앞에 아래 frontmatter를 넣고, 그 다음 줄부터 보고서 본문(제목 줄, 기준 시각 줄, 본문)을 적는다.

   ```yaml
   ---
   title: "AI·개발 도구 브리핑"
   task: ai-dev-briefing
   date: 2026-11-03
   generated_at: 2026-11-03T08:34:00+09:00
   level: notice
   summary: "보고서 결론 한 줄"
   headline: "검색 결과에 보일 제목"
   description: "검색 결과에 보일 설명"
   tags: ["Node.js", "CVE-2026-12345", "MCP"]
   ---
   ```

   - `title`: 작업 파일의 제목(첫 줄 `#` 제목)을 그대로 쓴다. 날짜와 대괄호는 넣지 않는다.
   - `task`: 작업 ID
   - `date`: 실행일의 KST 날짜 (저장 경로의 날짜와 같음)
   - `generated_at`: 보고서를 완성한 시각 (KST, `+09:00`)
   - `level`: 아래 기준 중 하나
   - `summary`: 보고서 맨 위 결론을 한 문장으로 요약하고 "~습니다"로 끝낸다. 큰따옴표로 감싸고, 안에 큰따옴표가 들어가면 `\"`로 쓴다.
   - `headline`: 검색 결과와 공유 카드에 보일 제목. 그날 다룬 핵심(제품명, 버전, CVE 번호 등 고유명사)을 앞에 두고 40자 안팎으로 쓴다. 날짜, 대괄호, "보고서" 같은 말은 넣지 않는다. 새 소식이 없는 날은 "주요 신규 소식 없음"을 넣되 참고로 다룬 항목이 있으면 함께 적는다.
   - `description`: 검색 결과에 보일 설명. 이 보고서가 무엇을 다뤘는지 80~150자의 자연스러운 문장 1~2개로 쓰고 "~습니다"로 끝낸다. `summary`를 그대로 복사하지 않는다.
   - `tags`: 보고서에서 다룬 기술, 제품, 회사, CVE 번호 3~8개. 공식 표기를 따르고(예: `Node.js`, `PostgreSQL`), "보안", "뉴스" 같은 일반 단어는 넣지 않는다. 1단계에서 읽은 이전 보고서에 같은 대상의 태그가 있으면 그 표기를 그대로 쓴다(사이트의 태그별 페이지가 표기로 묶인다).
   - frontmatter에 개인 정보나 확인되지 않은 수치를 넣지 않는다. 확인되지 않은 사건은 `headline`과 `tags`에 넣지 않는다.

   | 작업 | `urgent` | `notice` | `normal` |
   |---|---|---|---|
   | AI·개발 도구 브리핑 | 실무에 바로 영향 주는 변경(호환성 깨짐, 지원 종료, 보안 수정) | 주요 소식 있음 | 새 소식 없음 |
   | S&P500 실적·금리 아침 점검 | 결론이 `점검 필요` | 결론이 `주의` | 결론이 `영향 없음` |
   | IT 보안 이슈 데일리 리포트 | P1 이슈 있음 | P2 이슈만 있음 | P3 이하이거나 이슈 없음 |

4. **커밋·푸시**: 커밋 작성자는 실행 환경의 기본 설정을 그대로 쓴다(`git config`로 바꾸지 않는다). 보고서 파일만 `git add` 하고(보안 루틴이 후속 확인 항목을 올렸다면 `watch/watchlist.json`도) `report(<작업 ID>): YYYY-MM-DD` 메시지로 커밋한 뒤 `main` 브랜치에 push한다. push가 거부되면 `git pull --rebase origin main` 후 다시 push한다.
5. **알림**: 푸시 알림 도구(PushNotification)가 있으면 마지막에 한 번 보낸다. push에 성공했으면 `<title> · <level> · <summary>` 한 줄을 보내고, 실패했으면 실패 사실과 원인을 보낸다.
6. 보고서 파일 외의 파일(작업 파일, 이 규칙, 사이트 코드 등)은 수정하지 않는다. 예외는 두 가지다.
   - `watch/watchlist.json`: 보안 루틴(03)이 후속 확인 항목을 추가하고, 후속 확인 루틴(04)이 상태를 바꾼다.
   - 후속 확인 루틴(04)은 가장 최근 보안 리포트에 "후속 확인" 절을 넣을 수 있다.
