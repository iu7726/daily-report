## 5. 런타임·프레임워크

### ③ [P2] Fastify 프록시 플러그인 — 경로 우회와 Node.js 프로세스 종료

`@fastify/reply-from`은 상위 경로(`..`) 검사를 정확한 문자열 비교로만 해서, `..;` 처럼 세미콜론 경로 매개변수를 붙인 세그먼트가 검사를 통과합니다. 백엔드가 Tomcat·Jetty·Spring Boot처럼 세미콜론 매개변수를 지운 뒤 경로를 풀면, 프록시가 허용한 범위 밖의 백엔드 경로에 닿습니다.

`@fastify/http-proxy`는 WebSocket 지원을 켰을 때 세 가지 경로로 업그레이드 소켓에 오류 리스너가 빠집니다. 클라이언트가 연결을 끊거나 URL 조각(`#`)이 든 경로로 요청하면 처리되지 않은 오류로 Node.js 프로세스 전체가 종료됩니다. 인증 없이 원격에서 일으킬 수 있습니다.

`@fastify/http-proxy`는 WebSocket 지원(`websocket: true`)을 켠 경우만, `@fastify/reply-from`은 백엔드가 세미콜론 경로 매개변수를 지우는 Java 계열 서버일 때 실제 영향이 큽니다. Fastify 본체(`fastify` 5.12.8)는 해당하지 않습니다.

| 영향 버전 | 수정 버전 | 식별번호 | CVSS | KEV·실제 악용 |
|---|---|---|---|---|
| `@fastify/reply-from` 12.8.4 미만 · `@fastify/http-proxy` 9.0.0 ~ 11.6.9 | 12.8.4, 11.6.10 | CVE-2026-127064, CVE-2026-129500, CVE-2026-129502, CVE-2026-130647 | 8.2 / 7.5 (CVSS 3.1) | 미등재 · 확인 불가 |

> API 게이트웨이나 BFF를 Fastify 프록시로 만들었다면, 요청 하나로 게이트웨이 프로세스가 죽을 수 있습니다.

- 쓰고 있다면 `@fastify/reply-from` 12.8.4, `@fastify/http-proxy` 11.6.10으로 올립니다. `@fastify/http-proxy`는 내부에서 `@fastify/reply-from`을 쓰니 둘 다 확인합니다.

### ④ [P2] parse5 — 저(low) 서로게이트 두 개로 Node.js 프로세스 종료

HTML 파서 `parse5`가 연속된 저 서로게이트 문자(U+DC00 U+DC00)를 받으면 범위를 벗어난 코드 포인트를 만들고 `RangeError`를 던집니다. `parse`, `parseFragment`, 스트리밍 파서 모두 해당하고, 호출하는 쪽에서 예외를 잡지 않으면 Node.js 프로세스가 종료됩니다.

사용자가 보낸 HTML을 서버에서 파싱하는 경우(`jsdom`, `cheerio`, HTML 정제·미리보기·메일 처리 등 `parse5`를 쓰는 라이브러리 포함)가 대상입니다. 브라우저에서만 쓰거나 신뢰하는 HTML만 파싱한다면 영향이 작습니다.

| 영향 버전 | 수정 버전 | 식별번호 | CVSS | KEV·실제 악용 |
|---|---|---|---|---|
| 7.0.0 ~ 8.1.0 | 8.1.1 | CVE-2026-133245 | 8.7 (CVSS 4.0) · 7.5 (CVSS 3.1) | 미등재 · 확인 불가 |

> 간접 의존성으로 들어오는 경우가 많으니 `npm ls parse5`로 실제 설치 버전을 봐야 합니다.

- `parse5`가 8.1.1 미만이면 상위 패키지를 올리거나 `overrides`로 8.1.1 이상을 지정합니다(7.x는 메이저 호환성 확인 필요).
- 바로 못 올리면 파싱 호출을 `try`/`catch`로 감싸 프로세스가 죽지 않게 합니다.
- 원문: [parse5 수정 커밋](https://github.com/inikulin/parse5/commit/9b57bf87db292b54337554d2fd21b2a54f0f1a36) · [PR #1921](https://github.com/inikulin/parse5/pull/1921) (npm 8.1.1 배포 2026-11-08 06:41 KST, NVD 공개 2026-11-20 01:21 KST)

## 7. 공급망·CI/CD·인프라

### ① [P1] GitLab — Ruby2Shell, 인증 없는 원격 코드 실행에 수정판 없음

Ruby가 11월 18일 정규식 컴파일·매칭과 문자열 대소문자 변환의 메모리 취약점 7건을 고친 4.0.10 / 3.4.13 / 3.3.14를 냈습니다. Ruby 공지는 6건에 대해 일부 상황에서 원격 코드 실행을 보여 주는 PoC가 있다고 밝혔습니다. 발견자 Veria Labs는 "Ruby2Shell"이라는 이름으로, 기본 설정 Rails에서 인증 없이 이 경로에 닿는다고 발표했습니다.

Veria Labs는 GitLab 19.6.0 이하를 "Vulnerable, 수정판 없음"으로 분류했습니다. self-managed GitLab은 자체 Ruby를 품고 있어 서버의 Ruby만 올려서는 안 되고 GitLab 패치 릴리스가 필요합니다. GitLab의 최신 패치 릴리스는 11월 16일 19.5.6이고, 아직 GitLab 공식 공지는 없습니다. GitLab.com·Dedicated 사용자는 할 일이 없습니다.

| 영향 버전 | 수정 버전 | 식별번호 | CVSS | KEV·실제 악용 |
|---|---|---|---|---|
| Ruby 3.3.13 이하, 3.4.0 ~ 3.4.12, 4.0.0 ~ 4.0.9 · GitLab 19.6.0 이하(Veria Labs 기준) | Ruby 4.0.10, 3.4.13, 3.3.14 · GitLab 확인 불가(미출시) | CVE-2026-132825 외 6건(Ruby 공지는 GHSA-34m4-m9fh-gqp5 등) | 확인 불가 | 미등재 · 실제 악용 확인 불가(PoC 공개 11월 25일 예정) |

> 공개 PoC가 나오는 11월 25일 전에 GitLab 패치가 없을 수 있습니다. 인터넷에 직접 열린 self-managed GitLab은 오늘 접근 경로부터 줄여야 합니다.

- self-managed GitLab을 운영한다면 VPN·IP 허용 목록·SSO 프록시 뒤로 옮겨 외부에서 직접 닿지 않게 하고, GitLab 패치 릴리스가 나오면 바로 올립니다. 후속 확인 등록됨.
- 같은 서버나 CI 이미지에서 Ruby 앱(Rails, Sinatra)을 돌린다면 Ruby를 4.0.10 / 3.4.13 / 3.3.14로 올립니다. AWS는 Rack 기반 앱이 기본 요청 처리로 닿을 수 있다고 공지했습니다.
- 원문: [Ruby 보안 공지](https://www.ruby-lang.org/en/news/2026/11/18/multiple-vulnerabilities-in-regexp-and-string/) (2026-11-19 09:00 KST) · [Veria Labs Ruby2Shell](https://verialabs.com/ruby2shell/) (2026-11-20 07:59 KST 갱신) · [2026-193-AWS](https://aws.amazon.com/security/security-bulletins/rss/2026-193-aws/) (2026-11-20 08:05 KST) · [GitLab 패치 릴리스 목록](https://docs.gitlab.com/releases/patches/)

### ② [P1] NGINX — Amazon Linux·Elastic Beanstalk 패치 배포, WAF로는 못 막음

어제 P1로 다룬 NGINX HTTP/2 원격 코드 실행(CVE-2026-123007 외)에 AWS가 공지를 냈습니다. Amazon Linux 2·2023·2027용 패치 패키지가 나왔고, Elastic Beanstalk 수정도 배포됐습니다. AWS는 이 공격이 완전한 HTTP 요청이 만들어지기 전 HTTP/2 계층에서 일어나 AWS WAF 관리형·사용자 규칙으로 탐지하거나 막을 수 없다고 밝혔습니다.

Elastic Beanstalk는 사용자가 NGINX 리스너에 HTTP/2를 직접 켠 환경만 해당하고, 기본 구성은 HTTP/2를 켜지 않습니다. 그 밖의 EC2·컨테이너에 직접 설치한 NGINX는 어제와 같이 버전을 확인해야 합니다.

| 영향 버전 | 수정 버전 | 식별번호 | CVSS | KEV·실제 악용 |
|---|---|---|---|---|
| 1.30.7 / 1.31.9 미만 | 1.30.7, 1.31.9, Amazon Linux 패키지(ALAS) | CVE-2026-123007, CVE-2026-123633 외 4건 | 9.2 (CVSS 4.0) | 미등재 · 실제 악용 확인 불가 |

> WAF를 앞에 두었다고 안심하면 안 됩니다. NGINX 자체를 올려야 합니다.

- Amazon Linux라면 `sudo yum update nginx`로 올리고 NGINX를 다시 시작합니다.
- Elastic Beanstalk에서 HTTP/2를 켰다면 플랫폼 업데이트를 적용하고, 그 전까지 HTTP/2를 끕니다.
- 원문: [2026-192-AWS](https://aws.amazon.com/security/security-bulletins/rss/2026-192-aws/) (2026-11-20 08:00 KST) · [ALAS CVE-2026-123007](https://explore.alas.aws.amazon.com/CVE-2026-123007.html) · [nginx security advisories](https://nginx.org/en/security_advisories.html) (2026-11-18)

### ⑤ [P2] Git LFS 3.8.1 — 악성 저장소를 받기만 해도 명령 실행

Git LFS가 하위 모듈 설정 값의 줄바꿈 문자와 `.lfsconfig`의 옵션 키를 제대로 거르지 않아, 악성 저장소가 Git LFS에 공격자가 고른 명령을 실행시키게 할 수 있습니다(CVE-2026-105802, CVE-2026-105803). SSH URL 경로 인수 미인용(CVE-2026-69260)과 리다이렉트 후 다른 호스트로 쿠키를 보내는 문제(CVE-2026-69261)도 함께 고쳐졌습니다.

신뢰할 수 없는 저장소를 Git LFS가 설치된 환경에서 클론·fetch하는 경우가 대상입니다. 개발자 PC(Git for Windows·Homebrew에 함께 설치되는 경우가 많음)와 외부 PR을 받는 CI 러너가 해당합니다. 3.8.1은 10월 22일에 나왔고 이번에 NVD에 처음 올라왔습니다.

|---|---|---|---|---|
| 0.5.0 ~ 3.8.0 (항목별 시작 버전 다름) | 3.8.1 | CVE-2026-105802, CVE-2026-105803, CVE-2026-69260, CVE-2026-69261 | 8.6 / 8.6 / 7.6 / 7.6 (CVSS 4.0) | 미등재 · 확인 불가 |

- 3.8.1 미만이면 패키지 관리자나 Git for Windows 최신판으로 올립니다. 자체 CI 이미지에 Git LFS를 넣었다면 이미지도 다시 만듭니다.
