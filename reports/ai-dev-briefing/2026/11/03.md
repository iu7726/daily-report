### 2. GitHub Actions — 공개 저장소 `pull_request_target` 기본 차단, 일정 변경
- **발표일**: 2026-11-02 (GitHub Changelog)
- **핵심 변경**: 공개 저장소에서 `pull_request_target` 이벤트를 "applicable Actions event policy"가 명시적으로 허용하지 않는 한 기본 차단한다. 원래 11/2 시행 예정이던 일정이 바뀌어, 11/9·11/16 16:00~18:00 UTC 두 차례 브라운아웃(차단된 실행은 실패로 기록되고 워크플로가 실행되지 않음) 후 **2026-12-02 영구 시행**된다. 그 전까지는 경고만 남기는 evaluate 모드다. 비공개·internal 저장소와 GitHub Enterprise Server는 대상이 아니다.
- **원문**: https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2
- **개발자에게 주는 의미**: `pull_request_target`은 기본 저장소 컨텍스트에서 시크릿에 접근할 수 있어 포크 PR 공격 경로로 자주 쓰였다. 이 트리거에 의존하는 오픈소스 CI(포크 PR 라벨링, 미리보기 배포, 커버리지 코멘트 등)는 허용 정책을 걸지 않으면 멈춘다.
- **실무 적용 포인트**
  - 공개 저장소에서 `grep -rn pull_request_target .github/workflows`로 사용처를 찾고, Insights에서 차단 예정 실행을 확인한다.
  - 꼭 필요한 워크플로만 "workflow file targeting"으로 허용하고, 나머지는 `pull_request` + 최소 권한 `GITHUB_TOKEN`으로 바꾼다.
  - 브라운아웃 시각은 KST로 11/10·11/17 01:00~03:00이다. 야간 배포 파이프라인과 겹치는지 확인한다.

### 3. Anthropic — Claude Messages API "message threads" 베타
- **발표일**: 2026-11-02 (Claude Platform 릴리스 노트)
- **핵심 변경**
  - 베타 헤더 `message-threads-2026-08-12`. 첫 요청에 `"thread": {"type": "create"}`를 넣으면 대화가 서버에 저장되고, 이후에는 새 메시지만 보내며 `"thread": {"type": "continue", "previous_message_id": "<이전 응답 id>"}`로 이어 간다.
  - 스레드는 마지막 요청 후 5분에 만료되고, 마지막 사용 후 1시간 안에 삭제된다. 만료되면 continue 요청이 404를 반환하므로 전체 대화를 다시 create로 보내야 한다(SDK 헬퍼가 자동 처리).
  - continue 요청에 `system`·`tools`를 보내면 400. `model`, `tool_choice`, `thinking` 등 고정 필드가 다르면 `thread_fingerprint_mismatch` 오류. 요청당 `cache_control` 중단점은 최대 4개.
  - 요금·레이트 리밋은 바뀌지 않는다. Message Batches, compaction과는 함께 쓸 수 없고 ZDR 대상이 아니다.
  - Claude API, Claude Platform on AWS, Google Cloud(Anthropic 관리형), Microsoft Foundry에서 베타.
- **원문**: https://platform.claude.com/docs/en/release-notes/overview · https://platform.claude.com/docs/en/build-with-claude/message-threads
- **개발자에게 주는 의미**: 툴 호출이 수십 턴 이어지는 에이전트 루프에서 요청 크기와 첫 토큰 지연이 대화 길이에 비례해 늘어나는 문제를 줄인다. 다만 "best-effort" 저장이라 애플리케이션이 대화 원본을 계속 보관하고 재전송 경로를 가져야 한다.
- **실무 적용 포인트(TypeScript)**
  - SDK의 `client.beta.messages.thread({...})` 헬퍼로 `thread.send()`를 호출하면 create/continue/재전송을 대신 처리한다. 베타 tool runner도 기본으로 스레드를 쓴다(끌 수 있음).
  - 여러 인스턴스로 띄운 NestJS 서비스에서는 같은 API 키·워크스페이스로 요청해야 하며, 헬퍼는 메모리에만 대화를 보관하므로 Redis/DB에 대화 원본을 따로 둔다.
  - ZDR 계약이 필요한 서비스, 배치 처리 경로에는 적용하지 않는다.
