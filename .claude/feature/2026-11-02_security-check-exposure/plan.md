## 0. TL;DR

- 보안 점검 스킬을 처음 실제로 돌렸을 때(2026-11-02), Next.js 프로젝트 5곳이 설치 버전만으로 🔴 즉시 조치로 판정됐다. 그런데 사용처를 확인해 보니 리포트가 적은 공격 조건(`use cache`, Server Actions, glibc Linux에서 SVG 최적화)에 해당하는 곳이 없었다. 그래서 🔴라고 표시해 놓고 "내일 올려도 된다"고 안내하게 돼 표시와 안내가 어긋났다.
- 판정 전에 **노출 조건 확인**을 넣는다. P1 취약 버전이어도 사용처·노출 조건이 없으면 🟠로 내리고, 내린 항목은 **`🟠↓ 하향`**으로 따로 표시한다. 무엇을 확인했는지와 다시 🔴가 되는 조건도 함께 적는다.

- 사이트 변경: `web/components/SkillCallout.tsx`는 판정 기준을 싣지 않아 바꿀 것이 없다.

## 2. 현재 (사실 확인, 2026-11-02)

- `SKILL.md` 5단계 판정: 🔴 = "리포트 P1 대상이 **취약**으로 판정됨"이다. 설치 버전만 보고, 그 기능을 쓰는지는 보지 않는다.
- 첫 실행에서 사용처를 확인한 방법: 셸 `grep`을 손으로 돌렸다(`'use server'`, `'use cache'`, `next/image`, `next.config`의 `output`·`dangerouslyAllowSVG`, Dockerfile `FROM`). 이 과정에서 두 가지 문제가 있었다.
  - zsh에서 `--include=*.ts`가 글롭으로 풀려 검색이 실패했다.
  - 처음 검색을 `src`·`app`으로만 한정해 `lib`·`components`를 빠뜨렸다가 다시 돌렸다.
- 결과: Next.js 5곳 모두 세 공격 조건에 해당하지 않았다. 사용자가 "사용처가 없으면 주황으로 내려도 되는데 따로 표시만 해 주면 된다"고 정했다.

## 3. 결정 사항

### 확정 (사용자 2026-11-02)

- **D1. 사용처가 없으면 🟠로 내리고 표시한다**: 리포트 P1 대상이 설치 버전 기준으로 취약해도, 공격 조건이 프로젝트에 없으면 🟠로 내린다. 내린 항목은 `🟠↓ 하향`으로 표시해 원래 🔴였다는 것을 남긴다.

### 확정 (사용자 2026-11-02, 제안 승인 — D5는 `usage` 명령 포함으로 선택)

- **D2. 위치**: 5단계 '판정' 안에 "먼저 노출 조건 확인"을 넣는다. 단계 번호는 바꾸지 않는다.
- **D3. 하향 기준**
  - 리포트가 공격 조건(특정 기능·설정·OS·배포 형태)을 적었고, 그중 **필수 조건 하나 이상이 없다는 것을 코드·설정·배포 파일로 확인**한 경우에만 그 취약점을 '해당 없음'으로 본다.
  - 한 패키지에 P1 취약점이 여러 개면, **모두** 해당 없을 때만 내린다.
  - 리포트에 조건이 없거나("기본 구성에서 영향"), 확인할 수 없으면(배포 환경을 모르는데 그 조건이 배포 환경에 달린 경우 등) 🔴를 유지한다.
  - KEV 항목도 같은 기준을 쓰되, 결과에 KEV라는 사실을 그대로 남긴다.
- **D4. 결과 형식**
  - 결과 파일 맨 위에 표시 범례(🔴 / 🟠 / 🟠↓ / ✅)를 둔다.
  - `## 🟠↓ 하향` 절을 🔴 다음에 둔다. 항목마다 근거(원래 P1인 이유), **확인한 것**(검색한 패턴·파일), 하향 이유, **다시 🔴로 볼 때**, 제안 명령을 적는다.
  - 🟠(P2) 항목에서 사용처가 없으면 표시는 🟠로 두고 "사용처 없음"만 덧붙인다(✅로 내리지 않는다).
  - 대화 요약에는 🔴와 함께 🟠↓ 항목도 한 줄씩 보여 준다(원래 🔴였으므로).
- **D5. `collect.py usage` 하위 명령 추가 (권장)**
  - `--pattern 이름=정규식`을 여러 개 받아, 설정된 점검 대상의 프로젝트마다 일치하는 파일 수와 앞 몇 개 경로를 보여 준다.
  - `node_modules`·`.git`·`.next`·`out`·`dist`·`build` 같은 산출물 폴더는 건너뛰고, 소스·설정 확장자(`.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.json`, `.yml`, `.yaml`, Dockerfile)만 본다.
  - 이유: 첫 실행에서 손으로 돌린 검색이 셸 차이와 범위 누락으로 두 번 틀렸다. 점검 대상·제외 폴더를 inventory와 똑같이 맞출 수 있다.
  - 대안: 코드는 바꾸지 않고 SKILL.md에 `grep` 예시만 적는다. 더 가볍지만 첫 실행과 같은 실수가 다시 날 수 있다.

## 5. 케이스

- K1. 리포트에 공격 조건이 없음 → 🔴 유지
- K2. 필수 조건이 여러 개인 취약점(예: App Router **이고** Cache Components **이고** `use cache` 함수) → 하나라도 없으면 그 취약점은 해당 없음
- K3. 한 패키지에 P1 취약점이 여러 개 → 모두 해당 없을 때만 🟠↓
- K4. 코드에 사용처가 없음, 배포 환경은 모름 → 코드 조건이 없으므로 🟠↓ 가능
- K5. 코드에 사용처가 있음, 배포 환경을 모름(조건이 OS에 달림) → 🔴 유지
- K6. 문자열을 조합하는 식의 우회적인 사용은 검색으로 놓칠 수 있다 → '점검 한계'에 적는다
- K7. 다음 날 같은 항목 → 다시 확인한다(사용처는 코드가 바뀌면 달라진다). 이전 결과를 그대로 옮기지 않는다
