## 1. 긴급 — Linux IPv4 TCP 커널 RCE

- **원격·인증 불필요 RCE 가능성**
- AWS Security Bulletin 2026-160
- **CVE-2026-98432**

- 최초 AWS 공지: 10월 30일 22:15 PDT = **10월 31일 14:15 KST**
- 최신 갱신: 10월 31일 16:30 PDT = **11월 1일 08:30 KST**
- 영향: Linux Kernel 4.4 이후의 영향받는 버전 및 구성
- CVSS·KEV·실제 악용: 이번 확인 자료에서 확정되지 않음

Linux IPv4 TCP 핸드셰이크 경로에서 메모리의 수명 관리가 잘못되는 Use-After-Free 계열 문제다.

AWS 공식 설명에 따르면 특정 조건에서 인증되지 않은 외부 공격자가 조작한 IPv4 TCP 패킷을 전송해 **원격 코드 실행을 유발할 수 있다.**

즉, 일반적인 Node.js API가 취약해서 발생하는 사건이 아니라 운영체제 네트워크 스택의 보안 문제다.

### AWS 환경별 영향과 조치

| 운영 환경 | 대응 |
|---|---|
| **EC2 + Amazon Linux 2/2023** | 수정 커널 패키지 제공. 업데이트 후 재부팅 |
| EC2 + Ubuntu 등 다른 Linux | 해당 배포판의 보안 수정 패키지 확인·적용 |
| Docker on EC2 | 컨테이너가 아닌 **호스트 커널** 패치 |
| ECS on EC2 | ECS 최적화 AMI 또는 호스트 커널 갱신 |
| EKS | EKS 최적화 AL2023 AMI `v20261031` 이상 |
| ECS Fargate | AWS 측 수정 플랫폼 배포 진행 |
| ALB·CloudFront·API Gateway | AWS 관리형 인프라 패치 진행. 별도 고객 조치 없이 처리되는 영역 |
| RDS / Aurora | AWS 측 완화 조치 배포 중. 공개 DB 포트 차단 상태 확인 |

AWS는 ALB·CloudFront 등의 서비스를 통해 구성한 환경에서 직접 TCP 연결 노출을 줄일 수 있다고 안내한다. 다만 그 뒤의 EC2 인스턴스가 자동으로 패치된다는 의미는 아니다.

**Amazon Linux 긴급 패치**

```bash
# Amazon Linux 2
sudo yum update kernel
sudo reboot

# Amazon Linux 2023
sudo dnf update kernel --releasever=latest
sudo reboot
```

운영 서비스에서는 Blue-Green 방식으로 대체 인스턴스 또는 새 AMI를 검증한 뒤 트래픽을 전환하고 기존 인스턴스를 교체하는 방식 권장

**운영 판단:** 현재 사용하는 ALB 기반 무중단 배포 방식이라면 새 커널이 적용된 인스턴스를 먼저 띄워 Readiness 검사를 통과시킨 뒤 ALB 가중치를 전환하는 것이 적합하다. 기존 인스턴스를 한꺼번에 재부팅할 필요는 없다.

공식 원문: [AWS Security Bulletin 2026-160](https://aws.amazon.com/security/security-bulletins/2026-160-aws/)

## 2. AWS Kinesis Producer Library — IAM 자격 증명 노출

- 2026년 10월 31일 15:00 KST 공개 · AWS Security Bulletin 2026-159
- **CVE-2026-119117**

AWS가 Java용 Kinesis Producer Library(KPL)에서 AWS 인증 정보가 로그와 프로세스 명령행 인수에 노출되는 문제를 공개했다.

취약한 KPL은 DEBUG 로그에서 자격 증명을 기록할 수 있으며, 별도로 네이티브 자식 프로세스를 시작할 때 인증 정보를 명령행 인수로 전달한다. 로컬 사용자 또는 해당 로그에 접근할 수 있는 공격자가 인증 정보를 획득할 수 있다.

| 항목 | 내용 |
|---|---|
| 영향 패키지 | Java `amazon-kinesis-producer` |
| 취약 버전 | 기존 0.x 계열 및 1.0.8 미만 |
| 수정 버전 | **1.0.8 이상** |
| 공격 조건 | 프로세스 인수 또는 DEBUG 로그 접근 |
| 실제 악용·KEV | 공식 확인 없음 |

**완전한 해결은 1.0.8 이상으로 업그레이드하는 것이다.** 임시로 Daemon 로거를 INFO 이상으로 설정하면 로그 노출은 완화할 수 있지만, 명령행 인수 노출까지 제거되지는 않는다.

자격 증명이 외부에 노출된 정황이 있다면 장기 IAM Access Key를 교체하고, 필요한 경우 STS 세션을 무효화해야 한다. 로그 보관소도 점검 대상이다.

Node.js용 AWS SDK 자체의 취약점은 아니며, Java 기반 Kinesis 생산자를 사용하지 않는 환경에는 직접 영향이 없다.

공식 원문: [AWS Security Bulletin 2026-159](https://aws.amazon.com/security/security-bulletins/2026-159-aws/)

## 3. Node.js — Joi·Hapi 정규식 DoS

10월 28일 최초 공개 · 10월 30일 GitHub Advisory Database 등록

두 취약점 모두 특정 입력을 처리할 때 정규식 실행 시간이 입력 크기의 제곱에 비례하여 증가하는 문제다. Node.js의 단일 Event Loop를 장시간 점유할 수 있다.

| 취약점 | CVSS v3.1 | 수정 버전 |
|---|---:|---|
| `CVE-2026-118772` · Joi 다중 이메일 검증 | 7.5 | `joi` 17.13.9 / 18.3.1 |
| `CVE-2026-119202` · Hapi Content-Disposition | 7.5 | `@hapi/content` 6.0.3 |

**Joi:** `Joi.string().email({ multiple: true })`를 사용하면서 입력 길이 제한이 없다면, 긴 공백 문자열로 Event Loop를 차단할 수 있다. 레거시 `@hapi/joi` 16.0.0~17.1.1은 취약 범위이며 해당 패키지 자체의 수정판이 없어 `joi`로 이전해야 한다.

업그레이드 전에는 `.max()`를 `.email()` 앞에 적용할 수 있지만, `abortEarly: false`를 함께 사용하면 완화책이 제대로 작동하지 않을 수 있다.

**Hapi:** Multipart 요청의 `Content-Disposition`에 긴 비정상 매개변수를 포함시키면 헤더 파싱 중 CPU를 장시간 점유할 수 있다. `@hapi/content` 6.0.2 이하가 영향받으며, 단순 요청 크기 제한만으로는 완전히 해결되지 않는다.

두 사례 모두 공격 가능 경로가 공개되어 있으나 실제 운영 환경에서 악용된 사건은 확인되지 않았다.

**실무 영향:** NestJS에서 Joi를 사용해 요청값을 검증한다면 직접적인 점검 대상이다. Hapi 서버를 운영하지 않고 해당 패키지도 사용하지 않는다면 Hapi 취약점의 직접 위험은 낮다.

공식 원문: [Joi 보안 권고문](https://github.com/advisories/GHSA-4528-x5fx-h6hg) · [Hapi Content 보안 권고문](https://github.com/advisories/GHSA-8494-f6mr-cjpv)

## 5. npm·CI/CD — 레지스트리 인증정보 유출

10월 25~26일 최초 공개 · 10월 30일 GitHub DB 갱신

| 패키지 | CVE | 영향 버전 | 수정 버전 |
|---|---|---|---|
| `@sigstore/oci` | CVE-2026-118763 | 0.7.1 이하 | **0.7.2** |
| `follow-redirects` | CVE-2026-116689 | 1.16.0~1.16.1 | **1.16.2** |

`@sigstore/oci`는 컨테이너 레지스트리가 Blob 업로드 대상 URL을 다른 호스트로 지정할 경우, 기존 레지스트리 `Authorization` 헤더까지 전달할 수 있는 문제다. 공격자가 응답을 조작할 수 있는 환경이라면 Registry 인증정보가 유출될 수 있다.

`follow-redirects`는 다른 JavaScript Realm에서 생성된 `sensitiveHeaders` 배열을 제대로 처리하지 못해, 특정 교차 출처 리다이렉트에서 사용자 지정 인증 헤더가 전달될 수 있다.

**실무 영향:** ECR·OCI 이미지 배포, Sigstore 기반 아티팩트 검증, 외부 API를 호출하는 Node.js 코드에서 관련 패키지를 사용한다면 버전을 확인해야 한다. 단순히 Axios를 사용한다는 사실만으로 후자의 공격 조건이 충족되는 것은 아니다.

## 최종 판단

**오늘 가장 중요한 일은 Linux 커널 패치다.** AWS가 새로운 무인증 RCE 가능성을 공식적으로 공개했고, Amazon Linux 수정 커널까지 제공하고 있다. Blue-Green 배포 체계가 있다면 검증된 수정 AMI로 인스턴스를 교체하는 방식이 가장 적합하다.

그다음은 Node.js 애플리케이션의 `joi`, `node-forge` 및 인증 헤더 처리 라이브러리 점검이다. 특히 외부 사용자 입력이 정규식·인증서 파서·파일 업로드 처리로 들어가는 서비스라면 Event Loop 가용성과 인증 검증을 함께 확인해야 한다.

**핵심 요약:** 11월 1일은 기존 Brotli·GitLab 보안 이슈보다도 **새로 공개된 Linux 커널 IPv4 TCP RCE와 AWS 인프라 패치 상태**에 주의를 집중해야 하는 날이다. 현재 운영 서버의 버전이나 실제 침해 여부를 직접 검사한 결과는 아니므로, 위 명령과 AWS 보안 공지를 기준으로 배포 환경별 확인이 필요하다.
