# 보안 점검

보안 리포트는 클라우드 루틴이 매일 쓰지만, 클라우드는 이 컴퓨터의 프로젝트를 볼 수 없다. 이 스킬이 그 둘을 잇는다. 리포트에서 "어떤 패키지의 어떤 버전이 취약한지"를 뽑고, 로컬 프로젝트에 **실제로 설치된 버전**(lockfile 기준)과 대조해 프로젝트별로 조치할 것을 정리한다.

아래에서 `collect.py`는 이 SKILL.md와 같은 폴더의 `collect.py`다. 스킬을 불러올 때 표시되는 기본 폴더(Base directory) 경로를 붙여 실행한다.

## 지킬 것

- **읽기만 한다.** 패키지 설치·업데이트, `audit fix`, 파일 수정, 커밋, push를 하지 않는다. 업데이트 명령은 제안만 한다. 버전을 올리면 다른 것이 깨질 수 있어서, 언제 어떻게 올릴지는 사용자가 정한다.
- **결과를 공개된 곳에 남기지 않는다.** 결과에는 사용자 프로젝트(회사 프로젝트일 수 있음)의 취약 버전이 들어간다. 이 저장소는 공개 저장소일 수 있으니 결과 파일은 `collect.py outpath`가 알려 주는 경로에만 쓰고, 외부 서비스로 보내지 않는다.
- **audit는 사용자에게 물은 뒤에만 실행한다.** audit는 의존성 목록을 레지스트리로 보낸다. 회사 정책상 허용되는지는 사용자만 안다.
- **로컬 전용.** 클라우드 루틴 세션처럼 점검할 프로젝트가 없는 환경이면 그 사실만 알리고 멈춘다.
- **설정 파일(`config.local.json`)에는 개인 경로가 들어간다.** git에 올리지 않는다(이미 .gitignore에 있음).

## 절차

### 0. 점검 대상 확인

사람마다 프로젝트를 두는 방식이 달라서, 어디를 점검할지는 사용자가 한 번 정한다.

```bash
python3 <스킬 폴더>/collect.py config
```

**`설정 상태: 설정됨`이면** "점검 대상: …" 한 줄을 사용자에게 보여 주고 바로 1단계로 간다.

**`설정 상태: 설정 없음`이면** 아래 두 가지 중 고르게 한다(질문 도구가 있으면 그것으로). 출력의 "기본값 후보"와 "미리보기" 숫자를 함께 보여 주면 고르기 쉽다.

1. **자동**: 폴더 하나를 정하면 그 바로 아래 폴더들을 프로젝트로 보고 모두 점검한다. 프로젝트를 한곳(예: `~/dev`)에 모아 두는 경우. 건너뛸 폴더 이름도 받을 수 있다.
2. **지정**: 점검할 프로젝트 폴더를 직접 적는다. 프로젝트가 여러 곳에 흩어져 있거나 일부만 보고 싶은 경우.

고른 대로 저장한다. 설정은 스킬 폴더의 `config.local.json`에 저장되고 git에는 올라가지 않는다.

```bash
python3 <스킬 폴더>/collect.py config --auto ~/dev --exclude archive old-project
python3 <스킬 폴더>/collect.py config --list ~/work/api ~/work/web ~/side/blog
```

사용자가 "점검 대상 바꿔 줘"라고 하면 위 명령으로 다시 저장하고, `--reset`으로 지울 수도 있다. 이번 한 번만 다른 곳을 보려면 3·4단계 명령에 `--root <폴더>`나 `--path <폴더>`를 붙인다(설정 파일은 그대로).

### 1. 최근 보안 리포트 읽기

```bash
python3 <스킬 폴더>/collect.py reports            # 최근 3건, 더 보려면 --count 7
```

저장소의 원격(origin)을 fetch해 기본 브랜치의 리포트를 읽는다. 작업 중인 파일은 건드리지 않는다. 그래서 `git pull`은 하지 않아도 되고, 하지 않는다(pull은 지금 브랜치에 기본 브랜치를 병합한다). fetch가 실패하면 로컬 리포트를 읽었다는 안내가 나온다. 결과의 "리포트 출처"를 기억해 최종 결과에 적는다.

### 2. 점검 규칙 뽑기

리포트에서 **로컬에서 확인할 수 있는 대상**과 취약 범위를 뽑아 `이름:범위` 규칙으로 만든다.

- 대상: npm 패키지(`next`, `undici`, `react-server-dom-webpack` …), Node 런타임(`node`), 컨테이너 이미지(`nginx`, `postgres`, `redis` …)
- 범위는 "수정 버전 미만"을 비교식으로 쓴다. 메이저 라인이 여러 개면 `||`로 잇는다.
  - "16.x는 16.4.1 이상, 13~15.x는 15.5.28 이상" → `next:>=16.0.0 <16.4.1 || >=13.0.0 <15.5.28`
  - "Node 26.12.1 / 24.22.1 / 22.23.4로 업데이트" → `node:>=26.0.0 <26.12.1 || >=24.0.0 <24.22.1 || >=22.0.0 <22.23.4 || <22.0.0`
    (지원이 끝난 하위 메이저도 취약하다고 리포트에 적혀 있으면 마지막 구간처럼 넣는다)
- 규칙마다 리포트의 날짜, 우선순위(P1/P2), CVE·GHSA 번호를 따로 메모해 둔다. 5단계에서 근거로 쓴다.
- 리포트가 "미확인 보도"로 분류한 항목은 🟠까지만 올린다. 1차 자료로 확인되지 않은 것을 즉시 조치로 몰아붙이지 않기 위해서다.
- GitLab 자체 호스팅, Linux 커널, Ivanti 같은 서버·인프라 항목은 lockfile로 확인할 수 없다. 규칙으로 만들지 말고 "프로젝트 밖 점검 항목"에 따로 모은다.

### 3. 설치 버전 수집과 판정

```bash
python3 <스킬 폴더>/collect.py inventory \
  --check 'next:>=16.0.0 <16.4.1 || >=13.0.0 <15.5.28' \
  --check 'undici:<6.29.1 || >=7.0.0 <7.30.1' \
  --check 'node:>=24.0.0 <24.22.1 || >=22.0.0 <22.23.4'
```

- 점검 대상은 0단계에서 정한 설정을 따른다. 우선순위는 명령 옵션(`--root`, `--path`) > 환경 변수 `SECURITY_CHECK_ROOT` > 설정 파일 > 기본값(이 저장소의 상위 폴더, 자동)이다.
- 버전마다 `취약 / 안전 / 불명확 / 버전 해석 불가`가 붙는다. `불명확`은 `node:24`처럼 일부만 적힌 버전이 취약 범위와 일부만 겹친다는 뜻이다.
- 같은 패키지가 여러 버전으로 설치돼 있으면(중첩 의존성) 하나라도 취약하면 취약으로 본다.

### 4. audit 여부 묻기

아래 안내를 그대로 보여 주고 실행할지 묻는다. 질문 도구(AskUserQuestion)가 있으면 그것으로 "실행 / 건너뛰기"를 묻는다.

> **npm/pnpm audit를 실행할까요?**
> 보안 리포트에 없는 오래된 취약점까지 찾을 수 있습니다. 다만 실행하면 각 프로젝트의 **의존성 이름·버전 목록**이 npm 레지스트리로 전송됩니다(프로젝트에 사설 레지스트리 설정 `.npmrc`가 있으면 그 레지스트리로). 소스 코드는 전송되지 않습니다. 회사 정책상 외부 전송이 걱정되면 건너뛰세요. 건너뛰어도 보안 리포트 대조 결과는 그대로 드립니다.

동의하면:

```bash
python3 <스킬 폴더>/collect.py audit          # 특정 프로젝트만: --path <폴더> (여러 번 가능)
```

high·critical만 요약된다. 네트워크나 인증 문제로 실패한 프로젝트는 "audit 실패"로 남기고 넘어간다. 거절하면 이 단계를 건너뛰고 결과에 "audit 건너뜀"이라고 적는다.

### 5. 판정

**먼저 노출 조건을 확인한다.** 리포트 P1 대상이 **취약**으로 나왔으면, 🔴를 붙이기 전에 그 프로젝트가 취약한 기능을 실제로 쓰는지 본다. 버전만 보고 🔴를 붙인 뒤 "급하지 않다"고 안내하면 표시와 안내가 어긋난다.

1. 리포트에서 취약점마다 **공격 조건**을 뽑는다. 예: "App Router + `use cache` 함수", "glibc Linux에서 SVG 최적화", "Server Actions 사용", "신뢰할 수 없는 Brotli 데이터를 `node:zlib`로 풂"
2. 코드·설정에서 찾을 수 있는 조건은 `usage`로 찾는다. 점검 대상과 제외 폴더(node_modules, 빌드 산출물, lockfile, .env)는 inventory와 같다.

   ```bash
   python3 <스킬 폴더>/collect.py usage \
     --pattern "use cache=^\s*['\"]use cache" \
     --pattern "use server=^\s*['\"]use server['\"]" \
     --pattern "next/image=from ['\"]next/image['\"]" \
     --pattern "output=output:\s*['\"](export|standalone)['\"]"
   # 특정 프로젝트만: --path <폴더> (여러 번 가능)
   ```

3. 배포 형태(Dockerfile `FROM`의 alpine·debian, `output: 'export'`, CI 전용 여부)는 inventory의 런타임·이미지 단서와 `usage` 결과로 판단한다.

**하향 기준** (🔴 → 🟠↓)

- 리포트가 적은 필수 조건 중 **하나 이상이 없다는 것을 코드·설정·배포 파일로 확인**했으면 그 취약점은 해당 없음으로 본다.
- 한 패키지에 P1 취약점이 여러 개면 **모두** 해당 없을 때만 내린다.
- 리포트에 조건이 없거나("기본 구성에서 영향"), 조건을 확인할 수 없으면(예: 코드에서는 쓰는데 배포 OS를 모름) 🔴를 유지한다.
- KEV 항목도 같은 기준이다. 내리더라도 KEV라는 사실은 결과에 그대로 남긴다.
- 🟠(P2 등) 항목에서 사용처가 없으면 🟠를 유지하고 "사용처 없음"만 덧붙인다. ✅로 내리지 않는다.
- 사용처는 코드가 바뀌면 달라진다. 이전 점검 결과를 옮겨 쓰지 말고 매번 다시 확인한다.

| 표시 | 기준 |
|---|---|
| 🔴 즉시 조치 | 리포트 P1(실제 악용, CISA KEV, 인증 없는 원격 코드 실행) 대상이 **취약**이고 노출 조건이 해당하거나 확인할 수 없음, 또는 audit critical |
| 🟠↓ 하향 | 리포트 P1 대상이 **취약**이지만 노출 조건이 없다고 확인됨(원래 🔴). 확인한 것과 다시 🔴가 되는 조건을 함께 적는다 |
| 🟠 확인 필요 | 리포트 P2 대상이 취약, audit high, **불명확**·버전 해석 불가, lockfile이 없어 설치 버전을 모름, 미확인 보도 항목에 해당 |
| ✅ 해당 없음 | 규칙 대상이 없거나 모두 안전 |

판정은 "실제로 설치된 버전"을 기준으로 한다. `package.json`의 `^16.0.0` 같은 범위만으로 취약하다고 하지 않는다. 범위는 설치 버전이 아니라서 오탐이 많다.

### 6. 결과 작성과 저장

```bash
python3 <스킬 폴더>/collect.py outpath       # 기본: <점검 루트>/security-check/YYYY-MM-DD.md
```

이 경로에 아래 형식으로 결과를 쓴다. 대화에는 요약 표와 🔴 항목, 그리고 🟠↓ 항목(원래 🔴였으므로 왜 내렸는지 한 줄씩)을 짧게 보여 준 뒤 파일 경로를 알려 준다. `outpath`가 거부하면(저장소 안 경로) 기본 경로를 쓴다.

```markdown
# 보안 점검 — YYYY-MM-DD

기준 리포트: YYYY-MM-DD, … (출처: origin/main) · 점검 루트: <경로> · audit: 실행 / 건너뜀

> **표시**: 🔴 즉시 조치 · 🟠 확인 필요 · **🟠↓ 하향** = 설치 버전은 P1 취약 범위(원래 🔴)지만 노출 조건이 없다고 확인돼 내림 · ✅ 해당 없음

## 요약

| 프로젝트 | 상태 | 내용 |
|---|---|---|
| <폴더> | 🔴 | next 16.3.2 (CVE-…, KEV) |
| <폴더> | 🟠↓ | next 16.3.2 — 사용처 없음 (`use cache`·Server Actions 없음, alpine) |
| <폴더> | 🟠 | Node 24.x (Dockerfile, 버전 불명확) |
| <폴더> | ✅ | |

## 🔴 즉시 조치

### <폴더> — <패키지> <설치 버전> → <수정 버전> 이상
- 근거: <리포트 날짜> 보안 리포트 P1, <CVE/GHSA>, <KEV·악용 여부>
- 위치: <lockfile 경로>
- 노출: <해당하는 공격 조건, 또는 확인할 수 없는 이유>
- 제안: `npm install <패키지>@<수정 버전>` (pnpm이면 `pnpm up <패키지>@<수정 버전>`). 실행하지 않음

## 🟠↓ 하향 (P1 취약 버전, 노출 조건 없음)

### <폴더> — <패키지> <설치 버전> → <수정 버전> 이상
- 근거: <리포트 날짜> 보안 리포트 P1, <CVE/GHSA>, <KEV·악용 여부>
- 확인한 것: <찾아본 패턴·파일과 결과. 예: `use cache` 없음, Server Actions 없음, `node:24-alpine`(musl)>
- 하향 이유: <없다고 확인된 필수 조건>
- 다시 🔴로 볼 때: <예: `use cache`를 쓰기 시작할 때, glibc 이미지로 옮길 때>
- 제안: `npm install <패키지>@<수정 버전>`. 실행하지 않음
(여러 프로젝트가 같은 패키지면 프로젝트별 표 하나로 묶어도 된다)

## 🟠 확인 필요
(같은 형식, 확인할 점을 한 줄로)

## 프로젝트 밖 점검 항목
- 리포트의 서버·인프라 항목(예: GitLab 자체 호스팅, OS 커널)과 확인 방법
- Node 런타임·이미지 단서 중 확인이 필요한 것

## 점검 한계
- lockfile이 없는 프로젝트, audit 실패, 리포트 출처가 로컬이었던 경우 등
- 사용처 검색은 패턴 검색이라 문자열을 조합하는 식의 우회적인 사용은 놓칠 수 있다
```

## 자주 생기는 상황

- **리포트가 없음**: 저장소에 아직 보안 리포트가 없거나 fetch와 로컬 모두 실패한 경우다. 사용자에게 알리고, 원하면 audit만 한다.
- **프로젝트가 너무 많거나 느림**: 지정 모드로 바꾸거나, 자동 모드에 `--exclude`를 더하거나, `--max-depth`(기본 3)를 줄인다.
- **"찾을 수 없는 경로" 경고**: 지정한 폴더가 옮겨졌거나 지워진 경우다. 사용자에게 알리고 설정을 다시 저장한다.
- **모노레포**: 하위 `package.json`은 가장 가까운 상위 lockfile로 판정한다. audit는 lockfile이 있는 폴더마다 한 번만 돈다.
- **yarn 프로젝트**: 설치 버전 대조는 되지만 audit는 지원하지 않는다고 표시된다.
- **사용처 패턴이 너무 넓게 걸림**: 예를 들어 `multiple:\s*true`는 joi가 아닌 UI 속성에도 걸린다. `usage` 결과의 예시 줄을 보고 실제로 그 기능인지 확인한다. 애매하면 내리지 않는다.
